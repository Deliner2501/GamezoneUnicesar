# Exception Handling and Validation - Analysis

## 1. GameZoneException can be declared as Exception (checked) or RuntimeException (unchecked). Which option is more suitable for this project and why? What consequence does it have on the signatures of services and repositories?
**Answer:** `RuntimeException` (unchecked) is the better option. Errors such as a missing product, insufficient stock, or an invalid price cannot be fixed by the method that detects them; the only code that can do something useful with them is the user interface, which must tell the seller what happened. With a checked exception, every method between the validator and the menu (validator, service, menu action) would have to declare `throws` or catch it, spreading knowledge about errors through the signatures of all layers for no benefit. As an unchecked exception, it travels up freely and `MainMenu.start()` handles it in a single place. The consequence on signatures is that services, validators, and repositories declare nothing extra for `GameZoneException` and its subclasses. Some signatures still carry `throws IOException` from the earlier design, which is why the menu keeps a few local `catch (IOException)` blocks that the compiler requires. The cost of this choice is that the compiler no longer forces callers to handle these errors; the project mitigates it with one catch point in the menu, a `catch (GameZoneException)` fallback, and JavaDoc documenting what each method throws.

## 2. Why is it preferable to have a custom exception hierarchy with a common root class (GameZoneException) instead of throwing a generic IllegalArgumentException in every case? What design principles apply?
**Answer:** A generic `IllegalArgumentException` gives the same type to every failure, so the menu cannot tell a typing mistake from an empty inventory or a corrupted file; that was exactly the original problem, where every error produced the same indistinguishable message. The hierarchy turns the category of the failure into its type: `ResourceNotFoundException`, `BusinessRuleException`, `InvalidDataException`, and `PersistenceException`, each with its own error code (`RESOURCE_NOT_FOUND`, `BUSINESS_RULE_VIOLATION`, `INVALID_DATA`, `PERSISTENCE_ERROR`). The principles involved are: separation of concerns, because each type represents one category of failure; Protected Variations, because the menu depends on the stable root `GameZoneException`, so a new subtype is covered by the fallback without touching existing handlers; Open/Closed, because new categories are added by creating a class, not by editing existing code; Liskov substitution, because any subtype can be used wherever `GameZoneException` is expected; and information hiding, because `PersistenceException` hides technical `IOException` details from the user while preserving the original cause for traceability. The common root also separates the system's own errors from programming bugs such as `NullPointerException`.

## 3. The validators form a new layer (com.gamezone.validation). At what point in the flow are they invoked and why is this location coherent with the layered architecture? Can the validators access the persistence package? Justify.
**Answer:** Services invoke the validators at the start of each operation, before the business logic changes any state: `ProductService` validates product data before saving it, `PersonService` validates the data and the uniqueness of the identifier before registering a person, and `SaleService` validates stock availability and the sale data before the sale is built or persisted. This is coherent with the layered architecture because services orchestrate use cases while validators only hold pure rules, so the dependency direction stays `ui → service → validation → model`, with `persistence → model` as before and `exceptions` as a cross-cutting package usable from any layer. The validators must not access the persistence package, for three reasons: the project forbids file-access logic in validators; a validator that called a repository or a service would create a dependency back to the layer that invokes it, introducing cycles like the ones already found in the warranty module; and it keeps validators simple to reason about and test, since they receive the data already loaded as parameters (for example, `validateUniquePerson` receives the list of existing people instead of asking a DAO for it).

## 4. The refactor must preserve the system's external behavior. What strategy does the team follow to guarantee that the 10 menu operations keep working the same? What evidence is shown at the end to demonstrate that nothing broke?
**Answer:** The refactor is limited to two kinds of change: the type and wording of errors, and moving existing checks into validators with the same conditions. To keep behavior intact, the team worked in small atomic commits, compiling with `mvn compile` after each one, and kept safety nets in the menu: `IllegalArgumentException` is still handled for modules outside the refactor (accessories, promotions, returns, warranties) and for the defensive checks of the model, and `NumberFormatException` keeps its local handling because it concerns keyboard input. The evidence is a manual regression run of the 10 original operations on the same data files, once on `develop` before the feature and once on `feature/exception-handling`, comparing the output of the normal flow, plus the error scenarios that now show differentiated messages. The commit history also serves as evidence, since each commit changes only exception types, messages, or where a check lives.

## 5. ConsoleMenu used to catch a single generic exception. Now it must catch four different types. Is this done with a single try block with multiple catch clauses, with cascading catches, or with a general catch (GameZoneException)? Justify the choice considering code clarity and differentiation of messages to the user.
**Answer:** A single `try` with multiple `catch` clauses, placed at the one point where `MainMenu.start()` dispatches every menu option, followed by a `catch (GameZoneException)` fallback. A general `catch (GameZoneException)` alone would be the shortest option but would lose the differentiated messages, unless it inspected the type with `instanceof` or the error code, which reintroduces the type-checking that polymorphism is meant to avoid. Repeating a cascade of four catches inside each of the 20 or more menu methods would give precise handling but would duplicate the same ladder everywhere, and changing one message would mean editing every copy, with a real risk of inconsistencies. Because `GameZoneException` is unchecked, it can propagate from any menu action to `start()`, so one ladder covers all of them: each of the four types has its own `catch` calling a small helper with its message, the subclasses are listed before `GameZoneException` (the compiler rejects the reverse order), and the fallback guarantees that a future subtype reaches the user as a clear message instead of a stack trace. Local `catch` blocks remain only for what is genuinely local: `NumberFormatException` for keyboard input, and the `IOException` still required by some signatures, which now shows the same generic persistence message so the user never sees technical details.
