# Return Module - Analysis

## 1. A return is a new system entity that references an existing sale. What type of relationship exists between the Return class and the Sale class? Is this relationship inheritance, association, aggregation, or composition? Justify.
**Answer:** It is an **association** (specifically a directed reference, closer to aggregation than to composition). It is not inheritance, since a `Return` is not a kind of `Sale` — they are unrelated concepts that happen to be connected. It is not composition either, because composition implies that the "part" cannot exist independently of the "whole" and that destroying the whole destroys the part; here the opposite is true: the `Sale` exists on its own, was created and persisted long before any return, and continues to exist (and can be referenced by other returns) regardless of whether a `Return` is ever created for it. `Return` simply holds an immutable reference (`originalSale`) to a `Sale` object that it does not own or control the lifecycle of, which is the defining trait of an aggregation-style association: "a return references a sale," not "a return owns a sale."

## 2. A return can contain only some of the products from the original sale, not necessarily all of them. How is this reflected in the attributes of the Return class? What is stored in the returned-products attribute?
**Answer:** `Return` stores a `List<Product> returnedProducts`, which holds only the specific `Product` objects the customer is actually returning in that transaction — a subset of `originalSale.getProducts()`, not a copy of the full list. Nothing in `Return`'s attributes forces it to equal the original sale's product list; the constructor simply accepts whatever list `ReturnService.registerReturn` passes it, after that service has already validated that every product in the list genuinely belongs to the original sale. This is what allows a customer to buy three products and return only one: `returnedProducts` will contain a single `Product` object, while `originalSale.getProducts()` still has all three.

## 3. The business rule states that returns can only be registered within 30 days of the sale. In which layer of the system is this validation located, and why? What Java mechanism is used to calculate the difference between two dates?
**Answer:** The date-range calculation itself lives in the **model** layer, in `Sale.canBeReturned(LocalDate referenceDate)`, using `java.time.temporal.ChronoUnit.DAYS.between(date, referenceDate)` to compute the number of days elapsed since the sale. This mirrors the same pattern already used for `Promotion.isActive(LocalDate date)`: a single object should be able to answer a question about its own state (`Sale` already knows its own date) without needing a service to do that arithmetic for it. The **enforcement** of the rule — deciding to reject the operation when the check fails — belongs to the **service** layer, in `ReturnService.registerReturn`, which calls `originalSale.canBeReturned()` and throws an `IllegalArgumentException` if it returns `false`. This split keeps reusable domain logic in the model (any future feature that needs to know if a sale is still returnable can call the same method) while keeping the decision of *what to do* about that fact — a business rule that can change independently of the date math — in the service layer, consistent with the same separation used for promotions.

## 4. Returning products increases stock. What existing method from the Taller 1 system is reused for this operation, and in which class is it invoked from the return module? Why is it important to reuse existing methods instead of duplicating stock-update logic?
**Answer:** The method reused is `ProductDAO.update(Product)`, the exact same persistence method `SaleService.registerSale` already used to persist a stock change after calling `product.reduceStock(quantity)`. To make the reverse operation possible, a new but symmetrical method, `Product.increaseStock(quantity)`, was added to the model right next to `reduceStock`, and `ProductService.restoreStock(productId, quantity)` calls it and then persists the change through `productDAO.update(product)` — the same call path stock reduction already used. This method is invoked from `ReturnService.registerReturn`, once for each product being returned. Reusing `ProductDAO.update` instead of writing new file-access code for the return module matters for two reasons: it avoids having two different pieces of code responsible for writing the same file (`data/products.csv`), which could drift out of sync and produce bugs; and it respects the architecture rule that file-access logic belongs exclusively to the persistence layer, so `ReturnService` never needs to know *how* a product gets saved, only *that* it does.

## 5. The monthly balance report needs to consolidate information from two different modules (sales and returns). In which service class does this report live, and why is this location coherent with the layered architecture? What dependencies does this class need to generate it?
**Answer:** It lives in `ReturnService.generateMonthlyBalance(month, year)`, in the **service** layer. This is coherent with the layered architecture because consolidating information across two domain modules is a business-level concern, not something either `Sale` or `Return` should know how to do on its own — a model class representing one sale has no business summing up every sale in a month, and the UI should never perform that arithmetic itself, only display the result. Since `ReturnService` already depends on both `SaleService` (to resolve original sales) and `ProductService`/`ReturnRepository` (to resolve and persist returns), it already has every collaborator it needs: it calls `saleService.listSales()` to obtain and filter that month's sales by date and sum their final totals, and `returnRepository.loadAll()` to obtain and filter that month's returns and sum their refund amounts, then returns `totalSales - totalReturns`. No new dependency had to be added to make this possible, which is itself a sign the module's dependencies were designed correctly from the start.
