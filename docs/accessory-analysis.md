# Accessory Module - Analysis

## 1. Should accessories extend the existing Product hierarchy, or form an independent hierarchy? Justify your decision considering code reuse and model coherence.
**Answer:** Accessories should extend the existing `Product` hierarchy. All accessories share the same base attributes as any other sellable product (id, title, price, stock) and the same base behaviors (`reduceStock`, participating in a `Sale`). Creating an independent hierarchy would duplicate these attributes and methods, and would force `Sale` and `SaleService` to handle two unrelated item types instead of one. By extending `Product`, accessories are automatically compatible with the existing sales logic (`Sale` already stores a `List<Product>`), which keeps the model coherent and avoids code duplication.

## 2. What attributes are common to the three accessory types, and which are specific to each type? How is this distinction reflected in the module's class hierarchy?
**Answer:** The common attributes (id, title, price, stock) are already inherited from `Product`. On top of that, all three accessory types share one additional common attribute: the list of compatible console ids, since compatibility applies to controllers, cables and memories alike. This common attribute and its related behavior (adding a compatible console, checking compatibility) are placed in the abstract `Accessory` class. The type-specific attributes are declared only in each concrete subclass: `Controller` adds `connectionType`, `Cable` adds `lengthInMeters` and `connectorType`, and `Memory` adds `capacityInGigabytes` and `memoryType`. This mirrors the same pattern already used by `Product`/`VideoGame`/`Console`.

## 3. Compatibility between an accessory and a console is a relationship between two entities. How is this relationship represented in the design and in persistence? Is compatibility an attribute of the accessory, of the console, or of both?
**Answer:** Compatibility is modeled as an attribute of the accessory: each `Accessory` holds a `List<String>` of compatible console ids. This is a design choice, not the only valid one — it would be equally correct to store it on the console side, or as a separate association table, but keeping it on the accessory keeps the change additive, since it does not require modifying the existing `Console` class at all. In persistence, the list of console ids is serialized as a single CSV field per accessory row (ids separated by `;`), and reconstructed into a `List<String>` when the file is read back by `AccessoryDAO`.

## 4. What modifications are needed in SaleService so that sales can include accessories without breaking the existing behavior with video games and consoles?
**Answer:** Because `Accessory` extends `Product`, `Sale` does not need any change: it already stores a `List<Product>`, so an accessory is just another `Product` to it. The change belongs to `SaleService.registerSale`: instead of resolving every item id only through `ProductDAO`, it must also look the id up in `AccessoryDAO` when it is not found among products (or use a combined lookup that checks both DAOs). Stock validation and reduction should call the DAO the item actually came from (`ProductDAO` for `Console`/`VideoGame`, `AccessoryDAO` for `Controller`/`Cable`/`Memory`), but the validation rules themselves (no empty sale, stock must be sufficient, total is calculated from `Sale.products`) stay exactly the same, since they only depend on `Product`.

## 5. In which layer of the system's architecture should the new accessory classes be placed? Justify your decision based on the responsibilities of each layer.
**Answer:** Following the existing four-layer architecture: `Accessory`, `Controller`, `Cable` and `Memory` belong to the **model** layer, since they only represent data and domain behavior, with no file access logic. `AccessoryDAO` belongs to the **persistence** layer, since its only responsibility is reading and writing `data/accessories.csv`. `AccessoryService` belongs to the **service** layer, since it contains the business rules (validation, registering accessories, filtering by type, querying compatibility) and coordinates the persistence layer without exposing file details to the UI. Any new menu options belong to the **UI** layer (`MainMenu`), which only calls `AccessoryService` and never touches `AccessoryDAO` directly, respecting the established `ui -> service -> persistence -> model` dependency direction.
