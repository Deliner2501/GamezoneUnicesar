# Warranty Module - Analysis

## 1. The two warranty types share common attributes (dates, associated product) but also have different attributes and behaviors (duration, coverage, cost). How is this reflected in the class hierarchy design? What object-oriented mechanism allows each warranty type to have its own duration without duplicating code?
**Answer:** The shared state (id, product, sale, startDate, endDate) and shared behavior (isActive, generateWarrantyCertificate, getRemainingDays) live in the abstract base class `Warranty`, while what varies between types — duration, type name, and additional cost — is declared as **abstract methods** (`getDurationInMonths()`, `getWarrantyType()`, `getAdditionalCost()`) that each concrete subclass (`BasicWarranty`, `ExtendedWarranty`) must implement. This is the Template Method pattern enabled by **polymorphism and dynamic method dispatch**: the `Warranty` constructor calls `getDurationInMonths()` to calculate `endDate`, and because Java resolves that call at runtime based on the actual object's class, `BasicWarranty` automatically gets a 6-month end date and `ExtendedWarranty` a 12-month one, without the base class ever needing an `if/else` on warranty type or any code duplicated between the two subclasses.

## 2. The business rule states that only consoles generate an automatic basic warranty, not video games. In which layer of the system does this decision belong, and what Java mechanism is used to verify the real type of a product? Justify.
**Answer:** This decision belongs to the **service layer**, specifically inside `SaleService.registerSale()`, because it is a business rule about *when* to trigger warranty creation during the sale workflow — not a property of the product itself, nor a persistence concern. The mechanism used to check the real type of a product at runtime is Java's **`instanceof` operator** (`if (product instanceof Console)`), which safely tests whether a `Product` reference actually points to a `Console` object regardless of how it was declared, without needing to add a "type flag" field to `Product` or break encapsulation. This keeps the model layer free of sale-related logic (as required — no file access or business rules in `model` classes) while letting the service layer make the decision using the existing class hierarchy.

## 3. The duration of each warranty type is different (6 or 12 months). How is the expiration date calculated in each subclass? Should this calculation happen in the constructor or in a separate method? Justify.
**Answer:** The expiration date is **not** calculated separately in each subclass — it is calculated once, generically, in the `Warranty` base constructor: `this.endDate = startDate.plusMonths(getDurationInMonths())`. Each subclass only needs to implement `getDurationInMonths()` to return its own fixed number (6 for `BasicWarranty`, 12 for `ExtendedWarranty`); the actual date arithmetic is shared. This calculation belongs in the **constructor**, not in a separate method, because `endDate` is part of the object's core, immutable state: a `Warranty` should never exist in an inconsistent state where it has a `startDate` but no valid `endDate` yet. Computing it at construction time (and exposing only a getter, no setter) guarantees every `Warranty` instance is fully valid and consistent from the moment it is created, which matches the project's convention of immutable references for relationships that shouldn't change after creation.

## 4. The extended warranty adds a cost of 10% of the product's price to the sale total. At which point in the sale registration flow is this additional cost calculated and applied? What modifications are needed in the SaleService.registerSale method?
**Answer:** The cost is calculated **inside `ExtendedWarranty.getAdditionalCost()`** itself (`getProduct().getPrice() * 0.10`), but it is *applied* to the sale total in `SaleService.registerSale()`, after the sale has been created and stock has been validated: for each product in the sale, if it is a `Console` and the caller requested extended warranty for it, `registerSale` calls `WarrantyService.assignExtendedWarranty(product, sale, sale.getDate())` and adds the returned warranty's `getAdditionalCost()` to the sale's total. The required modifications to `registerSale` are: (1) accept an additional parameter, e.g. `List<String> productIdsWithExtendedWarranty`, defaulting to no extended warranties if null or empty; (2) after creating the `Sale` object, loop through its products and call `WarrantyService.assignBasicWarranty(...)` automatically for every `Console`; (3) for each `Console` whose id appears in `productIdsWithExtendedWarranty`, additionally call `WarrantyService.assignExtendedWarranty(...)` and increase the sale's total by the returned `getAdditionalCost()` before the sale is persisted.

## 5. Querying "warranties about to expire" requires iterating over all warranties and filtering those whose end date falls within the next 30 days. In which class does this method belong, and what dependencies does it need? Why is this location consistent with the layered architecture?
**Answer:** This method, `listWarrantiesExpiringSoon(int daysAhead)`, belongs in **`WarrantyService`**. It only needs a single dependency: `WarrantyRepository`, which it uses to load every persisted warranty via `loadAll()`; the filtering logic itself (comparing each warranty's `endDate` against today's date plus `daysAhead`) is plain business logic that doesn't require any other service. This location is consistent with the layered architecture because filtering-by-business-rule is exactly what the service layer is for: `WarrantyRepository` only knows how to read and write raw records (it shouldn't know what "about to expire" means), and the model class `Warranty` only exposes facts about a single instance (`isActive`, `getRemainingDays`) rather than aggregating over a collection. Keeping the "list and filter many warranties" logic in the service layer also keeps it reusable — the console menu can call it directly without duplicating the date-comparison logic itself.
