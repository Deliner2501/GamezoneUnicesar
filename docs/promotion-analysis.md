# Promotion Module - Analysis

## 1. The three promotions have different calculation rules but share common attributes and behaviors. How is this reflected in the class hierarchy design? Which object-oriented mechanism allows each promotion type to calculate its discount differently without the rest of the system knowing the concrete types?
**Answer:** The common attributes (id, name, startDate, endDate) and the common behavior (`isActive(LocalDate date)`) are placed in the abstract base class `Promotion`. Each concrete subclass (`PercentageDiscount`, `CategoryDiscount`, `BulkPurchaseDiscount`) only adds the attributes specific to its own calculation rule (percentage, target category, minimum quantity). The mechanism that allows the rest of the system to treat all three uniformly is **polymorphism** through the abstract method `calculateDiscount(Sale sale)`: `PromotionService` and any other class only ever call `promotion.calculateDiscount(sale)` on a `Promotion` reference, and Java dispatches the call to whichever concrete subclass the object actually is at runtime. This means new promotion types can be added later without changing any code that already works with `Promotion`.

## 2. The base class Promotion cannot implement the discount calculation method because each type has different logic. How is this method declared in the base class, and what does this declaration guarantee about the subclasses?
**Answer:** It is declared as an **abstract method**: `public abstract double calculateDiscount(Sale sale);`. Declaring it abstract in an abstract class means `Promotion` provides no implementation at all, and the Java compiler guarantees that every concrete (non-abstract) subclass **must** provide its own implementation, annotated with `@Override`. This is what allows `PromotionService` to call `calculateDiscount` on any `Promotion` object with the certainty that a valid, type-specific calculation will always run, without needing an `if/else` or `instanceof` chain to decide which logic applies.

## 3. The business rule states that only the promotion with the largest discount is applied. In which class does this selection logic live, and why is this location coherent with the layered architecture principle? Why should this logic NOT live in the Sale class or in the console menu?
**Answer:** This logic lives in `PromotionService.findBestPromotionFor(Sale sale)`, in the **service** layer. This is coherent with the layered architecture because business rules — decisions about *how* the store operates, such as "the best promotion wins" — are exactly the service layer's responsibility, while the model layer only represents data and per-object behavior, and the UI layer only collects input and displays output. Placing this logic in `Sale` would be wrong because `Sale` is a model class: it should not need to know about `Promotion` at all, and mixing in file-independent business rules would violate the single responsibility of the model layer and make `Sale` harder to reuse and test. Placing it in the console menu would be even worse, since UI classes should only orchestrate calls to services, never contain business logic — otherwise the same rule would have to be duplicated if another interface (e.g. a future web UI) needed to register sales too.

## 4. What modifications are needed in the Sale class and in the generateReceipt method so that the receipt shows the applied discount? Do these modifications break any existing behavior?
**Answer:** `Sale` needs two new private attributes, `appliedPromotionName` (String) and `discountAmount` (double), with their respective getters and setters, defaulting to `null`/`0.0` when no promotion applies. `generateReceipt` needs to be modified to print the subtotal (the sum of product prices, i.e. what `calculateTotal()` already computes), then a line showing the discount amount and the name of the applied promotion (or an indication that no promotion applied, if `appliedPromotionName` is null), and finally the adjusted total (subtotal minus discount). These changes are **additive**: existing sales that never received a promotion simply keep `discountAmount` at `0.0` and `appliedPromotionName` at `null`, so their receipts show a $0 discount and a total equal to the subtotal, exactly as before. No existing method signature changes, so no existing calling code breaks.

## 5. Active promotions are determined by comparing the current date with each promotion's start and end date. Where should this validation happen (in the Promotion class, in PromotionService, or in both)? Justify.
**Answer:** It happens in **both**, but each for a different reason. `Promotion.isActive(LocalDate date)` is where the actual date-range comparison logic lives, because it is a property of a single promotion and belongs in the model layer as domain behavior — this way any part of the system that has a `Promotion` object can check its validity without duplicating the comparison logic. `PromotionService.listActivePromotions()` and `findBestPromotionFor(Sale sale)` then *use* that method (calling `p.isActive(LocalDate.now())` for every loaded promotion) to decide which promotions to consider for a given operation. In other words, `Promotion` owns the rule of what "active" means, while `PromotionService` owns the decision of when and on which promotions to apply that rule — keeping the calculation reusable and the business orchestration separate from it.
